# lidar-edge-accel — LiDAR 전처리를 C++ 직렬 · OpenMP · CUDA로 구현하고 같은 결과인지부터 확인한 기록

실제 Velodyne HDL-64E 스캔(KITTI raw, 108장, 장당 약 12만 점)에 대해
**ROI 크롭·복셀 다운샘플 → RANSAC 지면 제거 → BEV 격자 연결 성분(클러스터)** 을
세 방식으로 구현하고, 단계별 지연과 **결과 일치**를 같은 조건에서 쟀다.

**브라우저에서 돌려 보기: https://mjholics.github.io/lidar-edge-accel/** — 같은 C++ 소스를 WebAssembly로 내서, 실제 스캔 12장을 손으로 돌리며 단계별로 본다(아래 8번).

| 구현 | 복셀 | RANSAC | 클러스터 |
|---|---|---|---|
| CPU 직렬 | 정렬 후 구간 평균 | 가설별 전수 계산 | BFS |
| CPU OpenMP (2·4·8·16) | 병렬 키 계산 + `__gnu_parallel::sort` + 구간 병렬 평균 | 가설 축 병렬 | BFS |
| GPU thrust | `sort_by_key` + `reduce_by_key` | 가설 1개 = 블록 1개, 공유메모리 리덕션 | 유니온-파인드(atomicMin) |
| **GPU 해시(직접 작성)** | open addressing 해시 + atomicCAS/atomicAdd | 같음 | 유니온-파인드 / 라벨 전파 |

## 1. 왜 했나

자율주행·로보틱스 인지 스택은 모델 앞단에 포인트클라우드 전처리가 붙는데, 10Hz LiDAR면 한 스캔 예산이
100ms이고 그 안에 검출·추적까지 들어가야 한다. 지금까지 한 경량화(TensorRT 132→316FPS, ONNX INT8)는
**라이브러리가 만든 커널을 고른 것**이었고, CUDA 커널을 직접 쓰거나 멀티코어 CPU를 직접 나눠 본 적은 없었다.
그래서 "무엇을 GPU로 옮겨야 이득인가"를 알고리즘 단위로 재 보기로 했다.

## 2. 누가 쓰나

차량·로봇 엣지 보드에서 LiDAR 인지를 돌리는 팀. 이 결과가 답하는 질문은 "GPU가 빠른가"가 아니라
**"어느 단계를, 어떤 알고리즘으로 옮겨야 지연이 줄고, 옮겨도 결과가 같은가"** 다.

## 3. 설계 근거

- **모든 구현이 같은 답을 내야 비교가 성립한다.** RANSAC 가설(점 3개 인덱스 256세트)은 호스트에서
  xorshift로 한 번 만들어 모든 구현이 공유하고, 동점이면 앞 가설을 고르는 규칙까지 맞췄다.
  클러스터 라벨은 "성분 안 최소 셀 인덱스"로 정규화해 배열 전체를 비교한다.
- **GPU 버퍼는 한 번만 잡는다.** 프레임마다 `cudaMalloc` 하지 않는 게 탑재 조건이라, 생성자에서 할당하고
  입력은 pinned 메모리에서 비동기로 올린다. 호스트→장치 복사(0.08ms)도 지연에 포함했다.
- **해시 복셀을 직접 쓴 이유**: 정렬 기반(thrust)은 12만 점 전체를 정렬하지만 필요한 건 복셀별 합뿐이다.
  해시 테이블(부하율 0.5 이하, 선형 탐사)에 atomicAdd로 바로 누적하면 정렬이 복셀 3만 개로 줄어든다.
  해시 순서는 실행마다 달라서, 가설이 같은 복셀을 가리키도록 마지막에 key로 정렬한다(이 비용도 포함).

## 4. 결과 (108장, 스캔마다 5회 반복의 중앙값 → 스캔 분포의 중앙값, ms)

환경: RTX 4080 SUPER · Ryzen 7 7800X3D(8코어 16스레드) · WSL2 Ubuntu 24.04 · CUDA 12.8 · g++ 13.3 `-O3 -march=native`

| 구현 | H2D | 복셀 | RANSAC | 클러스터 | 합계 | p95 | 직렬 대비 |
|---|---:|---:|---:|---:|---:|---:|---:|
| CPU 직렬 | – | 3.94 | 1.44 | 0.14 | 5.55 | 5.84 | 1.0× |
| CPU 2스레드 | – | 2.15 | 0.74 | 0.14 | 3.07 | 3.54 | 1.8× |
| CPU 4스레드 | – | 1.28 | 0.41 | 0.15 | 1.83 | 2.53 | 3.0× |
| CPU 8스레드 | – | 1.01 | 0.38 | 0.16 | 1.55 | 1.69 | 3.6× |
| CPU 16스레드(SMT) | – | 1.09 | 0.29 | 0.18 | 1.57 | 2.01 | 3.5× |
| GPU thrust + UF | 0.08 | 0.81 | 0.06 | 0.20 | 1.26 | 1.63 | 4.4× |
| **GPU 해시 + UF** | 0.08 | **0.27** | 0.06 | 0.21 | **0.70** | 1.16 | **7.9×** |
| GPU 해시 + 라벨 전파 | 0.08 | 0.28 | 0.06 | 12.32 | 12.58 | 21.68 | 0.44× |
| GPU 해시 + 전파(16회마다 확인) | 0.08 | 0.27 | 0.06 | 3.94 | 4.40 | 9.68 | 1.26× |

입력 규모(중앙값): 점 122,301 · 복셀 30,233 · 지면 15,955 · 클러스터 81.
합계는 호스트 벽시계(동기화·런치 포함), 단계 값은 CUDA 이벤트 구간이다.

**일치 검증**: 8개 구현 모두 108장 전부에서 복셀 수·키, RANSAC 최적 가설·인라이어 수, 지면 수,
클러스터 라벨 배열(4만 셀)이 CPU 직렬과 **완전히 같았다.** 다른 건 복셀 중심의 부동소수 오차뿐이다
(최대 7.6e-6m — GPU는 atomicAdd·트리 리덕션이라 더하는 순서가 다르다).

### 읽은 것

- **단계마다 GPU 이득이 다르다.** 직렬 대비(스캔별 비율의 중앙값) RANSAC 26배, 복셀 14배인데 **클러스터는 0.7배(오히려 느림)** 다.
  4만 셀 격자는 CPU BFS가 0.14ms면 끝나서 옮길 이유가 없다. GPU에 두는 이유는 데이터가 이미 GPU에 있어서
  왕복 복사를 안 하려는 것 하나뿐이다.
- **같은 GPU에서도 알고리즘이 64배를 가른다.** 연결 성분을 라벨 전파로 풀면 긴 벽·연석 같은 성분 때문에
  수렴까지 **79~205회(중앙 159회)** 반복하고 12.3ms가 걸린다. 유니온-파인드는 병합·압축 커널 두 번(0.21ms)이다.
- **그 64배 중 약 2/3는 동기화였다.** 수렴 플래그를 매 반복 호스트가 읽는 대신 16회마다 읽게 바꾸자
  결과는 그대로 12.3ms에서 3.9ms로 줄었다. nsys에서 `cudaStreamSynchronize` 중앙값은 37µs였다.
  남은 3.9ms(160회 런치, 반복당 약 23µs)는 반복 횟수 자체의 비용이라, 유니온-파인드와 남은 20배는 알고리즘 차이다.
- **CPU는 8스레드(물리 코어 수)에서 멈춘다.** 16스레드는 중앙값이 같고 p95만 1.69에서 2.01ms로 나빠졌다.
- **10Hz 예산(100ms) 대비로는 전부 여유다.** 이 수치는 데스크톱 기준이라 엣지 보드의 절대값으로 옮길 수 없다.
  옮겨지는 건 비율과 구조다 — 어느 단계가 GPU에서 이득인지, 동기화 횟수가 지연을 얼마나 좌우하는지.

## 6. 에러 대처

- **OpenMP를 켰더니 2~8스레드가 직렬보다 느렸다.** 전체 108장에서 복셀 단계가 직렬 3.88ms, 2스레드 7.41,
  4스레드 7.47, 8스레드 6.15ms였고 p95는 17ms까지 튀었다. 그런데 16스레드만 1.29ms로 정상이었다.
  16만 정상이라는 게 단서였다 — `__gnu_parallel::sort`는 `num_threads` 절이 아니라 `omp_get_max_threads()`(16)를
  따른다. 키 계산 영역은 2스레드, 정렬은 16스레드, 평균 영역은 다시 2스레드로 **병렬 영역마다 팀 크기가
  바뀌면서** 스레드 풀을 계속 다시 만들고 있었다. `omp_set_num_threads(threads)`로 맞추자 2스레드 2.15ms,
  4스레드 1.28ms, 8스레드 1.01ms가 됐다. 수정 전 빌드(`-DFIX_SORT_THREADS=0`)를 남겨 `results/nofix_*`로 재현된다.
- **FMA 걱정은 기우였다.** nvcc는 기본으로 곱셈·덧셈을 합쳐(FMA) 한 번만 반올림하고 g++(`-std=c++17`)은
  따로 반올림해서, 임계값 경계의 점이 GPU와 CPU에서 다르게 판정될 수 있다. `--fmad=false`로 다시 빌드해
  108장을 돌렸지만(`results/nofma_*`) 두 빌드 모두 인라이어 수 차이 0건이었다. 이 데이터에서는 경계에 걸린
  점이 없었다는 뜻이지 보장은 아니라서, 검증 CSV를 매 실행 남기게 했다.
- **WSL2의 nsys는 GPU 커널 트레이스를 주지 않았다.** API 통계만 나와서 커널 시간을 직접 분리하지 못했고,
  대신 수렴 확인 주기를 바꾸는 실험(위 16회 변형)으로 동기화 비용을 간접 분리했다.
- 준비 단계: WSL에 nvcc가 없어서 CUDA 12.8 툴킷을 새로 설치했고, KITTI zip을 풀 `unzip`도 없었다.
  Git Bash에서 `wsl.exe`에 경로를 넘기면 `/mnt/c`가 `C:/Program Files/Git/mnt/c`로 바뀌어 PowerShell로 실행했다.

## 7. 개발 순서

1. JD 갭 확인: CUDA 커널 직접 작성·멀티코어 병렬·포인트클라우드 — 기존 프로젝트에 `.cu` 0개, OpenMP 0개
2. 툴체인·데이터 준비(CUDA 12.8, KITTI raw drive 0001)
3. CPU 직렬 기준 구현 → OpenMP → GPU(thrust, 해시, UF, 전파) 순으로 추가, 매 단계 직렬과 비교
4. 5장 스모크 → OpenMP 역전 발견·수정 → 108장 본측정 + FMA 끔 + 수정 전 대조
5. 라벨 전파의 지연 원인 분리(nsys API 통계 → 16회 확인 변형)

## 8. 브라우저에서 돌려 보기 (`web/`)

직렬 CPU 경로(`src/cpu_ops.cpp`)를 고치지 않고 Emscripten으로 WASM(22KB)으로 냈다. 열면 12장이 저절로 넘어가며
원본 점 → 복셀 → 바닥 → 물체 순으로 색이 바뀌고, 끌어서 돌릴 수 있다. 서버는 없고 계산은 보는 사람의 기기에서 돈다.

| 확인한 것 | 값 |
|---|---|
| WASM과 네이티브의 일치(12장 × 10항목: 복셀 키·중심 해시, 최적 가설, 인라이어·지면 수, 클러스터 라벨 4만 칸 해시 등) | 120/120 (`web/tests/parity.test.mjs`, 화면에서는 `?selftest=1`) |
| 같은 입력 한 장 처리 시간 — PC 크롬 WASM / g++ `-O3` / g++ `-O3 -march=native` | 11 / 7.14 / 5.40 ms |
| 실은 데이터 | ROI 안 점만(96.5%), 좌표를 16비트로(한 점 16 → 6바이트, 한 장 0.7MB) |

- **좌표를 1.2mm 단위로 줄였더니 물체 수가 달라졌다.** 복셀 수는 최대 26개(3만 중)만 달라졌는데 클러스터 수는 12장 중앙값 14.5개,
  최대 29개 달랐다(`results/pack.log`, 예: 102 → 73). 점이 1mm 미만으로 움직였을 뿐인데 RANSAC이 다른 평면을 골랐기 때문이다.
- 그래서 **같은 입력에서 RANSAC 시드만 50번 바꿔** 봤다(`results/web_seed_spread.csv`, 12장의 중앙값).

  | 가설 수 | 256 | 1,024 | 4,096 |
  |---|---|---|---|
  | 클러스터 수의 폭(최대 − 최소) | 51 | 39.5 | 28 |
  | 지면 복셀 수의 폭 | 827 | 309.5 | 119.5 |

  가설을 16배로 늘리면 지면 수는 잡히는데 클러스터 수는 여전히 28개씩 흔들린다. 평면 하나가 경사·연석을 다 덮지 못해
  지면 조각이 물체로 남는다. 4번의 "구현 간 완전 일치"는 같은 시드에서의 일치이고, 이 값은 그 결과 자체가 얼마나 불안정한지다.
  화면의 「같은 장면, 바닥 다시 찾기」가 이걸 그대로 보여 준다. 브라우저에서 4,096번은 한 장에 90~136ms(PC 크롬에서 두 번 잼)라 10Hz 예산을 다 쓴다.
- 대조 정답은 `-ffp-contract=off`로 냈다(WASM에는 FMA가 없다). 이 12장에서는 `-march=native` 빌드와도 10항목이 전부 같았다.
- 화면을 붙이다 찾은 것: 물체 색을 고르는 해시에서 `^`가 음수를 내 팔레트 밖을 읽었다. 테스트가 라벨 2개만 봐서 통과했고,
  실제 라벨(셀 번호 0~39,999)을 넣자 죽었다 → 부호 없는 값으로 고치고 테스트를 4만 개 전수로 바꿨다.

```bash
bash scripts/setup_emsdk.sh && bash scripts/build_web.sh   # 프레임 줄이기 → 대조 정답 → WASM
bash scripts/seed_spread.sh
node --test web/tests                                       # 21개
```

## 범위

- 데스크톱 GPU·CPU 측정이다. Jetson 같은 엣지 보드에서는 재지 않았다.
- 데이터는 KITTI 한 드라이브(108장, 도심 주행)다. 다른 장면에서 전파 반복 수는 달라진다.
- 지면은 평면 하나로 본다. 경사·굴곡이 있는 도로는 격자별 지면 추정이 필요하다.
- 클러스터링은 BEV 격자 연결 성분이다. 점 단위 유클리드 클러스터링(kd-tree)은 구현하지 않았다.
